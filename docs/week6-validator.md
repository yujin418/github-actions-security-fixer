# 6주차: 수정안 검증 및 결과 제공 (validator)

- 기간: 11/2~11/8 (README 개발 계획 기준) · 문서 작성일: 2026-11-07
- 주제: 수정안이 반영된 워크플로우를 재분석해 **유효성·취약점 해소·변경 범위**를 검증하고, 결과를 PR 코멘트 형식으로 정리한다.
- 범위: 검증 판정과 결과 포맷까지. **실제 PR 게시(GitHub API 쓰기)와 실제 LLM 연동은 다음 단계.**

## 1. 이번 주 목표

5주차에서 만든 수정안이 "올바른 수정"인지 자동으로 판정하는 `app/validator`를 구현한다.
프로젝트 평가 계획(파일 형식 유효성 / 취약 패턴 해소 / 불필요한 변경)과 대응하도록
검증 항목을 세 가지로 나누고, 결과를 PR 코멘트용 마크다운으로 제공한다.

## 2. 검증 항목

| # | 항목 | 판정 방법 |
| --- | --- | --- |
| 1 | **형식 유효성** | 수정안 텍스트가 유효한 YAML(매핑)으로 파싱되는가 |
| 2 | **취약점 해소** | 재분석 시 대상 규칙의 탐지가 사라졌는가(건수 감소) |
| 3 | **변경 범위** | 수정으로 새 취약점(before에 없던 탐지)이 생기지 않았는가 |

세 조건을 모두 만족하면 `passed = True`. 하나라도 어긋나면 **검토 대상**으로 남긴다.

## 3. 구현한 것

| 파일 | 내용 |
| --- | --- |
| `app/validator/__init__.py` | `ValidationResult`, `validate_fix`, `format_pr_comment` |
| `tests/test_validator.py` | 유효/무효 YAML·해소/미해소·새 취약점·PR 코멘트 테스트 6건 |

`ValidationResult` 필드: `format_valid`, `resolved`, `new_findings`, `passed`, `detail`.

## 4. 처리 흐름

```text
원본 워크플로우 + 수정안이 반영된 워크플로우
  -> (1) 형식 검사: YAML 파싱
  -> (2)(3) 재분석: analyze_text(before) vs analyze_text(after)
       - 대상 규칙 탐지가 줄었는가(해소)
       - before 에 없던 탐지가 생겼는가(새 취약점)
  -> ValidationResult(통과/검토)
  -> format_pr_comment: 탐지·수정안·검증을 PR 코멘트 마크다운으로
```

## 5. 설계 결정

- **"적용된 결과 텍스트"를 입력으로** 받는다. 수정안을 워크플로우에 반영(apply)하는 단계와 검증을 분리해, 네트워크·LLM 없이 검증을 **오프라인으로 테스트**할 수 있게 했다.
- **재분석에 기존 엔진 재사용**: `analyze_text`를 그대로 호출해 "탐지 → 수정 → 재탐지"의 일관성을 유지한다.
- **보수적 통과 기준**: 형식·해소·무신규 세 조건을 모두 만족할 때만 통과. 일부만 만족하면 자동 반영하지 않고 검토로 남긴다(2주차 설계 원칙과 일치).
- **결과 제공은 포맷까지만**: `format_pr_comment`로 마크다운을 생성하고, 실제 PR 게시는 GitHub API 쓰기가 필요하므로 다음 단계로 둔다.

## 6. 검증 결과

```text
python -m pytest        # 29 passed (분석 10 + 서버 6 + fixer 7 + validator 6)

# 데모: unpinned 수정안 검증 + PR 코멘트
검증: 형식 유효 · 해소 예 · 새 취약점 0건 | passed = True

## 🔒 GitHub Actions 보안 점검 결과
### [MEDIUM] Unpinned Actions — ...unpinned-actions.yml:15
- 탐지 근거: `uses: actions/checkout@v4`
- 수정안: actions/checkout@<40-hex-sha>  # v4
- 이유: 태그는 이동 가능하므로 SHA로 고정
- 검증: ✅ 통과 (형식 유효 · 해소 예 · 새 취약점 0건)
```

## 7. 한계와 다음 단계

알려진 한계:
- 수정안(스니펫)을 워크플로우에 **자동 반영(apply)하는 단계는 아직 없다** — 현재는 반영된 텍스트를 입력으로 받는다.
- 새 취약점 판정은 `(rule_id, evidence)` 비교라, 편집으로 근거 문자열만 바뀐 경우의 정밀도는 제한적이다.
- 실제 PR 게시와 실제 LLM 연동은 **미수행(다음 단계)**.

다음 단계:
1. 수정안을 워크플로우에 반영하는 apply 단계(또는 LLM이 전체 파일 반환) 연결.
2. 탐지→수정안→검증→**PR 코멘트 게시**(GitHub API 쓰기)로 파이프라인 연결.
3. 실제 LLM 연동 검증(7주차 "전체 기능 연동" 주간 예정).
