# GitHub Actions 워크플로우 취약점 자동 수정 도구

GitHub Actions Workflow의 보안 취약 패턴을 탐지하고, **AI 수정안과 검증 결과를 GitHub Pull Request(PR)에 제공하는 도구**입니다.

> 개발 초기 단계의 프로젝트입니다. 아래 기능과 일정은 구현 목표입니다.
> 현재는 초기 3개 패턴에 대한 **규칙 기반 탐지**(`python -m app.analyzer`)까지 동작하며,
> LLM 수정안 생성·검증·PR 연동과 Webhook 서버는 아직 제공하지 않습니다.

## 프로젝트 소개

GitHub Actions는 테스트·빌드·배포를 자동화하지만, Workflow의 입력 처리나 권한 설정, 외부 Action 사용 방식에 따라 보안 문제가 발생할 수 있습니다.

이 프로젝트는 위험한 설정을 찾아 **무엇을 왜 수정해야 하는지 설명하고, 수정 후에도 기존 작업이 정상적으로 동작하는지 확인하는 것**을 목표로 합니다.

수정안 생성과 제안까지 자동화하며, 실제 반영 여부는 사용자가 검토합니다. 자동 병합은 범위에 포함하지 않습니다.

## 주요 기능

| 기능 | 설명 |
| --- | --- |
| **취약 패턴 탐지** | Workflow를 규칙 기반으로 분석하여 문제 위치와 탐지 근거 제공 |
| **AI 수정 제안** | 분석 결과를 바탕으로 수정안과 변경 이유 생성 |
| **수정안 검증** | 형식 검사, 취약점 재분석 및 테스트 환경에서 동작 확인 |
| **GitHub 연동** | PR에 수정 전후 차이와 검증 결과 제공 |

기존 도구에도 탐지와 일부 자동 수정 기능이 있으므로, AI 도입 자체보다 **수정 결과의 적절성과 검증 근거를 제공하는 과정**에 중점을 둡니다. 실제 개선 효과는 기존 도구 및 규칙 기반 수정과 비교하여 확인할 계획입니다.

## 분석 대상 및 범위

개인 테스트용 저장소의 `.github/workflows/` 내 YAML 파일을 대상으로 합니다.

| 초기 대상 | 분석 내용 |
| --- | --- |
| **Script Injection** | 신뢰할 수 없는 입력이 실행 스크립트에 직접 삽입되는 패턴 |
| **Excessive GITHUB_TOKEN Permissions** | 작업에 필요한 범위보다 넓게 설정된 토큰 권한 |
| **Unpinned Actions** | 커밋 SHA로 고정되지 않은 외부 Action 참조 |

초기 3개 유형의 대표 패턴을 중심으로 탐지 기능을 구현하고, 수정안 생성·검증·결과 제공을 연결합니다.

탐지 조건과 자동 수정 가능 조건은 구분합니다. 수정에 필요한 정보가 부족한 경우에는 검토 대상으로 남기며, 구현 결과에 따라 지원 조건을 조정합니다.

**확장 대상:** Pwn Request, Artifact Trust  
초기 기능의 통합 테스트와 주요 오류 수정을 우선하고, 여유가 있으면 일부 패턴 탐지를 추가합니다.

## 시스템 구성

```text
GitHub PR 이벤트
       ↓
Webhook 수신 및 요청 검증
       ↓
Workflow 파일 수집
       ↓
규칙 기반 취약점 분석
       ↓
AI 수정안 및 변경 이유 생성
       ↓
수정안 검사 및 재분석
       ↓
PR에 수정 제안과 검증 결과 제공
```

| 기술 | 역할 |
| --- | --- |
| **Python · FastAPI** | 백엔드 API, 이벤트 수신 및 처리 흐름 제어 |
| **Semgrep** | 규칙 기반 Workflow 정적 분석 |
| **LLM API** | 수정안과 변경 이유 생성 |
| **GitHub REST API · Webhooks** | 이벤트 전달, 파일 조회 및 PR 결과 제공 |

LLM 제공자와 모델, 의존성 버전 및 데이터 저장 방식은 구현 과정에서 결정합니다.

## 검증 및 평가 계획

취약 예제와 정상 예제를 함께 구성하고, 탐지와 수정 결과를 나누어 평가합니다.

| 항목 | 확인 기준 |
| --- | --- |
| **탐지 결과** | 취약 패턴 탐지 여부, 정상 설정에 대한 오탐 및 미탐 |
| **수정 효과** | 파일 형식과 설정의 유효성, 대상 취약 패턴의 해소 여부 |
| **기능 유지** | 테스트 저장소에서 수정 전후 작업의 정상 동작 여부 |
| **변경 범위** | 문제와 관계없는 불필요한 변경 여부 |

기존 도구와 지원 범위가 겹치는 항목에는 동일한 예제를 적용합니다. 수정 방식이 명확한 경우에는 규칙 기반 수정과 AI 수정도 비교합니다.

검증 결과는 **통과·실패·미수행**으로 구분합니다. 일부 검사 통과만으로 전체 안전성을 보장하지 않으며, 확인하지 못한 사항을 함께 표시합니다.

실행 테스트는 비밀정보가 없는 개인 테스트 환경에서 진행하고, 자동화 범위는 구현 과정에서 구체화합니다.

## 프로젝트 구조

```text
app/
├── main.py          # 애플리케이션 진입점
├── webhook/         # 이벤트 수신 및 요청 검증
├── analyzer/        # Workflow 분석 및 탐지 결과 정리
├── fixer/           # 수정안과 변경 이유 생성
├── validator/       # 수정안 검증 및 재분석
├── github/          # GitHub API 연동
└── database/        # 결과 저장 — 도입 여부 미정
rules/               # 보안 탐지 규칙
tests/               # 테스트 코드 및 Workflow 예제
docs/                # 학습·설계 문서
.github/workflows/   # 프로젝트 자체의 Workflow
requirements.txt
README.md
```

기능별 모듈을 분리하고, 세부 구현 파일은 개발 과정에서 추가합니다.
